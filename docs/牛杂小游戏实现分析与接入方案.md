## 2. 实现分析

### 2.1 整体架构：GUI 算数据，C++ 插件执行

两个小游戏都**不走普通任务流水线**，而是复用 `TaskType.MiniGame` → Core 的 `CustomTask` 入口，参数以 JSON 塞入，任务内 `register_plugin` 挂插件，由插件循环「截屏 → 识别 → 点击」执行：

```
GUI (C# WPF)
  PixelPaintHelper.cs   原图 → 24×24 色号矩阵 → 按色分组点列
  ToolboxViewModel.cs   调参 / 实时预览 / 拖拽滑动画布
        │ AsstPixelPaint(groups, swipe, gridDelay)
        │   → TaskType.MiniGame + params.pixel_paint（JSON）
        ▼
AsstProxy (C#)
        │ AsstAppendTask → AsstStart()
        ▼
Core (C++)  CustomTask.cpp
        │ set_params 解析校验（颜色 0~39、坐标 0~23 越界丢弃）
        │ register_plugin<PixelPaintTaskPlugin>()
        │   / register_plugin<SecretFrontTaskPlugin>()
        ▼
插件 _run() 循环：ctrler()->get_image() → 识别 → ctrler()->click/swipe → 回报进度（AsstMsg::SubTaskExtraInfo）
```

- 像素画：点列数据量大且与图像强相关 → **GUI 算好**，经 JSON 传给 Core（`params.pixel_paint.groups` = `[{color, points:[{x,y}]}]`）。
- 隐秘战线：每次选卡的 OCR 与决策都在 Core 内完成，GUI 只传任务名 `MiniGame@SecretFront@Begin@EndingA@支援作战平台`（CustomTask 解析结局与事件 token，见 `CustomTask.cpp::parse_and_register_secretfront`）。

### 2.2 像素画（PixelPaint）

**坐标配置外置**（`resource/tasks/MiniGame/PixelPaint.json`，720p 基准）：

| 任务 | 字段 | 含义 |
|------|------|------|
| `MiniGame@PixelPaint@Grid` | specialParams=[295,119,856,680] | 画布外框 left/top/right/bottom |
| `MiniGame@PixelPaint@PaletteTop` | [989,1060,1130,1200, 285,355,425,495,565,635] | 色板顶态：4 列 x + 6 行 y（色 0~23） |
| `MiniGame@PixelPaint@PaletteBottom` | [989,1060,1130,1200, 299,369,439,509,579,649, 4] | 色板底态 + `bottom_first_global_row=4`（色 24~39） |
| `MiniGame@PixelPaint@PaletteScrollToTop/Bottom` | specificRect 锚点 + Swipe | 上下滑动色板 |
| `MiniGame@PixelPaint@EditorCheck` | MatchTemplate + ROI | 编辑页识别闸（模板图） |

色号 → 格子坐标：`row = color/4, col = color%4`（色板 4 列 × 10 行，分顶/底两段展示 40 色）。

**图片 → 点列流水线**（`Helper/PixelPaintHelper.cs`，Maa-Web 前端可平移此算法）：

1. `TrimBorder`：裁透明/近白（RGB≥250）边
2. `SampleToGrid`：Fit 模式（Crop/Contain/Stretch）映射 24×24；每格**线性光空间面积平均**（防 sRGB 平均交界偏暗）+ 保留格内子样；取景区外填白
3. CSS 风格滤镜：亮度 → 对比度 → 饱和度（各 50~200% 滑块）
4. 量化（4 种）：None / FloydSteinberg（蛇形扫描 + 60% 误差强度）/ Atkinson / **Illustration 插画优先（默认）**——OKLab 感知空间 medoid 代表色 + 3 轮 ICM 迭代 MRF 平滑（邻格原图色近则倾向同色，strength=0.0012, sigma2=0.0025 指数衰减软约束）
5. 最近色匹配全在 **OKLab** 空间（40 色预转换缓存）
6. `BuildGroups`：按色分桶 `groups[color] → [(x,y)...]`（纯白默认跳过）→ 预览图 + 点列

**执行**（`src/MaaCore/Task/MiniGame/PixelPaintTaskPlugin.cpp`）：

- `verify()`：拦截 `SubTaskStart` + 任务名以 `MiniGame@PixelPaint@Begin` 结尾
- `in_editor_page()`：MatchTemplate 校验编辑页
- 两阶段绘制：先滚到顶画色 0~23，再滚到底画 24~39（滚动各 2 次保险 + 150ms sleep）
- 线段合并：同色同行的连续格合并，`len≥3` 用 `swipe` 拖画（20ms/格 + gridDelay），`len<3` 逐格点击；拖动后终点补点一次
- 防跑飞：每画 10 格（累计）重新识别一次编辑页
- 进度：`SubTaskExtraInfo` 回调 `PixelPaintProgress`(done/total/color) → GUI 日志

**GUI 交互**（ToolboxViewModel + ToolboxView.xaml）：拖拽/选图导入 → 实时预览（调参即时重算，`PreparedImage` 复用避免重复解码）→ Link Start 下发；KeyDown 支持画布缩放平移预览。

### 2.3 隐秘战线（SecretFront）

**策略数据硬编码**在 `SecretFrontTaskPlugin.cpp`：

- 5 条结局路线（A~E），每条 4 个阶段节点：
  `A: 1A→2A→3A→4A`、`B: 1A→2A→3A→4B`、`C: 1A→2A→3B→4C`、`D: 1A→2B→3C→4D`、`E: 1A→2B→3C→4E`
- 每阶段三属性（物资/情报/医疗）达标线：`1A:(20,20,20)、2A:(60,55,45)、2B:(45,55,65)、3A:(200,155,155)、3B:(150,220,250)、3C:(155,255,240)`
- 结局目标：`A:(510,350,350)、B:(440,440,350)、C:(350,550,350)、D:(365,475,495)、E:(370,385,620)`

**执行**（`SecretFrontTaskPlugin.cpp`，`verify()` 拦截任务名判定模式）：

- `SelectTeam`：按结局选分队（A/B→物资、C→情报、D/E→医疗）
- `Actions`（数值卡）：每张卡固定卡位（3 张时 x=200/553/907, y=311）RegionOCRer 识别三属性 + 完成百分比（失败按 100% 兜底）→ 从当前页往后翻 2 页全局比较（`ClickNextPage`），按「阶段缺口加权」打分选最优卡（`choose_best_card`：权重 = 各属性缺口/缺口和，分数 = Σ gain[k]×权重）→ 翻回目标页点击 2 次
- `Event`（文本卡）：OCR 卡左上角阶段名（`1A/1B/2A…`，正则过滤 + replace 映射），选路线中的卡，都不中保底第一张；`only_current_page`（预点击探测到指定事件时）不翻页
- 卡数估算：3 张→2 张递减尝试「全部卡可读」，失败兜底 1 张

**配置外置**（`resource/tasks/MiniGame/SecretFront.json`，31 项）：全部 ROI / Number OCR 任务 / 翻页点击 / 队伍选择等。

**GUI 侧**（ToolboxViewModel）：结局下拉（A~E）、事件下拉（支援作战平台/游侠/诡影迷踪，硬编码本地化三元组）、任务列表按「当前活动/常驻」分组（`miniGame` 条目的 `DisplayKey/TipKey` 本地化，无本地化时显示 `Display`/`Value` 原文）。

### 2.4 任务下发（GUI → 引擎）

```csharp
// 像素画：短任务入口 + params.pixel_paint 分组点列
AsstPixelPaint(groups,  swipeEnabled, gridDelay)
  → AsstCustomTask { CustomTasks=["MiniGame@PixelPaint@Begin"], Params={ pixel_paint: { swipe, grid_delay, groups:[{color, points:[x,y]}] } } }

// 隐秘战线：任务名编码结局与事件
AsstMiniGame("MiniGame@SecretFront@Begin@EndingA@支援作战平台")
```

Core 解析（`CustomTask.cpp`）：像素画校验 color 0~39、坐标 0~23、畸形点丢弃（防 C ABI 越界）；隐秘战线解析 `@EndingX` 与事件名 token。

## 3. 小游戏如何随活动开放/关闭变动（关键！）

### 3.1 数据源

小游戏列表**不是写死在前端**——来自游戏活动数据文件，随 MAA 引擎资源一起更新：

```
StageActivityV2.json   ←  https://api.maa.plus/MaaAssistantArknights/api/gui/StageActivityV2.json（备用 api2.maa.plus）
  └── CN (按 clientType: CN/CNB/txwy/YoStarEN/...)   ← B 服映射到官方
       └── miniGame: [...]   ← 活动专属小游戏条目，每项可含：
             { Display, DisplayKey, Value, Tip, TipKey,
               MinimumRequired, Activity,
               UtcStartTime, UtcExpireTime, TimeZone }   （"yyyy/MM/dd HH:mm:ss" 格式）
```

参考样例（结构同 stages/sideStoryStage，来自 ActivityData 数据流）：

```json
{
  "miniGame": [
    { "Display": "像素画小游戏", "DisplayKey": "MiniGameNamePixelPaint",
      "Value": "MiniGame@PixelPaint", "TipKey": "...Tip",
      "UtcStartTime": "2025/08/01 16:00:00", "UtcExpireTime": "2025/09/15 03:59:59", "TimeZone": -8 }
  ]
}
```

### 3.2 过滤逻辑（客户端 StageManager.cs + MiniGameEntry.cs）

1. **构建**：`InitializeDefaultMiniGameEntries()` 内置 5 个常驻项（3 商店 + 隐秘战线）打底；`ParseMiniGameEntries()` 把 `miniGame` JSON 数组（或单对象）解析进列表**最前**（活动项永远显示在常驻项上面）
2. **开窗过滤**：`BeingOpen = !NotOpenYet && !IsExpired`，即 `UtcStartTime <= now(UTC) <= UtcExpireTime`；解析失败的时间视为 MinValue（即「无限制」→ 常显）。**未开放/已过期条目不加入列表**
3. **版本门控**：`MinimumRequired`（SemVer）比当前客户端版本大时，条目仍显示但 Tip 标注「版本过低」并**禁启用**
4. **更新时机**：GUI 启动时 `UpdateStageLocal()`（读本地缓存 = 上次下载的 StageActivityV2.json）+ 手动/自动 `UpdateStageWeb()`（下载新文件、清缓存标记、growl 提示），更新完后整表重建（活动项重新过滤）
5. **本地化**：`DisplayKey/TipKey` → 本地化表；未命中的显示 `Display/Value` 原文

> 关键结论：**游戏侧新增/下架一个小游戏 = 更新 StageActivityV2.json 的 miniGame 段（+ 引擎包新增对应 MiniGame/*.json 任务资源 + 模板图）**。客户端代码无需改动，条目自动出现/消失。MAA 的资源包 OTA（changes.json 增量）会把这两个文件推到用户端。

### 3.3 引擎侧资源如何到端

- 活动小游戏的 任务 JSON（`MiniGame/XX.json`）、模板图（`template/MiniGame/...`）随 **MaaResource 资源包**（引擎 OTA）分发；
- 客户端用 `gui/StageActivityV2.json` 拉列表元数据，两条链路由 MAA 的更新源机制（GitHub / MirrorChyan）统一管理。

## 4. Maa-Web 接入方案

### 4.1 现状契合点（可直接复用，无新架构）

| Maa-Web 已有能力 | 位置 | 对小游戏的可用度 |
|---|---|---|
| StageActivityV2 拉取 + 6h 缓存 + 备用源 + 代理 | `backend/app/engine/stages_today.py` | **直接复用**：同一文件已含 `miniGame` 字段（当前只解析了 sideStoryStage/resourceCollection），加解析器即可 |
| 引擎包 / 动态资源双源更新（S-07） | `resource_mgr.py` + 更新路由 | 任务 JSON 随 OTA 到达，无需额外通道 |
| Custom 任务通道 | `asstproxy.to_asst_task()` | 像素画 / 隐秘战线走 CustomTask，与 Copilot 同层，可平级接入 |
| 工具箱三识别模式（任务执行 + extra_info 收集） | `backend/app/engine/toolbox.py` | 小游戏可复用同一「会话通道 + 事件收集」模式 |
| 设备 / 队列 / 日志基础设施 | `taskrunner.py` | 直接复用 |

### 4.2 三种接入路径

#### 方案 A：内置模块（推荐，与 MAA 客户端同构）

在 `backend/app/engine/` 新增 `minigame.py` + `backend/app/api/v1/` 新增 `minigame.py`，完全复刻客户端三层：

- **列表层**：解析 StageActivityV2 的 `miniGame`（按客户端 BuildServer → CN/CNB）∪ 内置常驻表（隐秘战线 + 像素画置为常驻兜底），`BeingOpen` 过滤 + `MinimumRequired` 版本门控 + 剩余天数；输出 `{value, display, tip, days_left, open}`。挂到现有 `GET /resources/stages/today` 或新端点
- **参数层**：
  - 像素画：前端（Vue）移植 `PixelPaintHelper.cs` 算法（线性光采样 + OKLab 量化 + 3 种抖动 + 插画 MRF），生成 `groups` JSON → `Custom` 任务下发（对齐客户端 `AsstPixelPaint` 的 `params.pixel_paint` 结构）；后端仅做校验
  - 隐秘战线：下拉选结局/事件（事件表需硬编码 3 个本地化元组，或随 StageActivityV2 扩展）→ 任务名 `MiniGame@SecretFront@Begin@Ending[A-E](@Event)?` 下发
- **执行层**：引擎包内自带 `MiniGame/*.json` 与插件（libMaaCore），Maa-Web **零实现**执行逻辑；进度经 extra_info（PixelPaintProgress）透传到前端日志区（复用工具箱日志通道）

依赖：引擎包必须 ≥ 含该插件的版本（MAA v6.16.8 已含）；`MiniGame/*.json` 随动态资源 OTA 到达后即可用。

#### 方案 B：Maa-Web 插件体系（预留扩展位）

为「新玩法小游戏 / 第三方小游戏」做通用入口：`minigame` 注册表（value → handler），handler = 前端参数面板 + 后端执行器组合；当前只注册 pixel_paint / secret_front 两个内置 handler，未来新游戏不改核心代码、加注册项即可。适合「活动频繁新增玩法」的长期演进，但要先定义注册表 / 面板描述 DSL，首期成本高于 A。

#### 方案 C：纯前端降级先上线（最快，非完整）

只做列表 + 隐秘战线（参数只有一个下拉，前端零算法），像素画留「规划中」。适合先验证链路：数据通道 → 任务下发 → 执行。

### 4.3 推荐路线（组合拳）

1. **首期（最小闭环，对应方案 C + A 的骨架）**
   - `stages_today.py` 增加 `miniGame` 解析 + 缓存复用；新端点 `GET /api/v1/minigames`（开放中列表）
   - 前端工具箱「牛杂」页：列表 + 结局/事件下拉 + LOG 区；下发 `MiniGame@SecretFront@...` 走现有 Custom 通道
   - 真机验证隐秘战线全流程（含 SelectTeam、事件页、翻页选卡）
2. **二期（像素画，对应方案 A 完整）**
   - 前端移植 `PixelPaintHelper` 全套算法（TS：OKLab + 面积采样 + FS/Atkinson/Illustration 量化），本地预览画布（拖拽/缩放/调参实时刷新）
   - 下发 `MiniGame@PixelPaint@Begin + params.pixel_paint`；后端只做校验透传
   - 真机验证：24×24 填色完整 + 色板两段滚动 + 进度回报
3. **三期（演进为方案 B 的注册表形态）**
   - 等第 2 个玩法类功能出现时抽象插件注册表；活动条目的 `Value→handler` 映射从 StageActivityV2 的字段驱动（或内置映射表）

### 4.4 关键风险与对策

| 风险 | 对策 |
|---|---|
| 像素画算法移植量大（量化/插画模式 OKLab MRF） | 首期只移植 None/FS 两档，Illustration 二期；或后端 Python 实现算法、前端只传图（增加一次上传，但后端可精确对齐 C# 逻辑并用 pytest 测色号矩阵） |
| 活动任务 JSON 依赖引擎包版本（MiniGame/PF.json 等） | 任务资源随动态资源 OTA；列表层加 `minimum_required` 检查，缺失资源时条目置灰提示「需更新资源」 |
| 小游戏活动窗口与 StageActivityV2 刷新（6h 缓存）不同步 | 首日开服前 6h 内可能延迟；可在 `minigame` 端点强制短缓存（如 30min）或手动刷新按钮（客户端也是手动更新） |
| 隐秘战线 OCR 中文/小字依赖引擎识别 | 引擎 RegionOCRer 已内置；只需保证分辨率 ≥720p（现有预检已拦） |
| 新活动新增小游戏时 Maa-Web 需同步？（不） | 走 StageActivityV2 + 资源 OTA 即自动出现，代码零改动（方案 A/B 都能保证，方案 C 的硬编码事件表除外——事件表也建议随 JSON/常量表维护） |

### 4.5 与客户端对照的落地清单

- [ ] `stages_today.py`：`_parse_minigames()`（对齐 ParseMiniGameEntries，`BeingOpen`/`MinimumRequired`）
- [ ] 新端点 `GET /api/v1/minigames`（或并入 stages/today 响应 `minigames` 段）
- [ ] 前端工具箱「牛杂」页（列表分组：进行中活动 / 常驻；结局+事件下拉；日志区复用）
- [ ] `minigame.py`（engine）：`resolve_pixel_paint(groups)` 校验 + Custom 下发；`resolve_secret_front(ending, event)` 任务名构造
- [ ] 像素画算法移植（TS 或 Python）→ 单测（色号矩阵快照比对，可对拍 C# 输出）
- [ ] 真机验收：隐秘战线 A/E 结局各通一局；像素画 24×24 全彩图完整填色
- [ ] 活动开/关自动化验证：mock StageActivityV2 时间窗，列表 出现/消失 正确
